## 再生成する手順

標準Python 3.10以上とNode 22以上で、候補生成と主要テストを再実行できます。生成処理そのものはネットワーク不要です。

```sh
python scripts/generate_sengoku_master.py
python scripts/build_migration_preview.py
python scripts/build_person_quality_review.py
python scripts/validate_sengoku_master.py
python -m unittest discover -s tests -p 'test_*.py' -v
node --test tests/runtime.test.js
```

最新版のGoogle Sheetから「人物データ」タブをCSVとして保存した場合：

```sh
python scripts/register_master_ids.py --input /path/to/person-master.csv
python scripts/generate_sengoku_master.py --input /path/to/person-master.csv --out /path/to/candidate
python scripts/validate_sengoku_master.py --input /path/to/person-master.csv --data /path/to/candidate
```

新規の名簿IDは台帳へ明示的に登録します。除外しても台帳からIDを削除せず、再採用時に再利用します。氏名変更は同一性を確認して台帳の `nameAtRegistration` だけを更新し、`id` を変えません。別名の自動同一視やファジーマッチによる統合は行いません。I列の値を再利用・振り替えないことが前提です。新規人物への旧ID継承は `oldIds` の明示的レビューが必要です。

品質確認の補正は `research-review.json` へ別管理し、元の人物情報を変えると確認時の入力SHAが不一致になり、確認済みの状態を引き継ぎません。H列の採否変更だけで確認内容を失うことはありません。

URL疎通を再調査する場合は別途 `python scripts/check_master_sources.py`、集計は `python scripts/audit_source_metadata.py` を実行します。疎通の結果は時点に依存するので入力アーティファクトとして固定し、JSON生成時に外部通信を行いません。

現行史跡・カードが後で増えたら、**新しいmainコミットからbackupを更新し、SHAと旧ID台帳をレビューしてから再生成**してください。今回の固定バックアップを新しいmainへ無条件にかぶせないでください。
